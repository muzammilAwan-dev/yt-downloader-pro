## 1. The product (what the code does today)

- **Extension** (`extension/`, MV3, v6.4.9): `background.js`, `content.js` (large, floating download button, builds the yt-dlp command), `popup.js/html` (popup UI; **duplicates the ytdlp:// handoff code**), `sites.js` (per-site rules; Vimeo now forwards the logged-in session cookies automatically), `logger.js`, `manifest.json` (no `nativeMessaging` permission; has a `commands` shortcut with a mac key). Sites: YouTube, Instagram, Facebook, X, TikTok, Reddit, Twitch, Vimeo, SoundCloud.
- **Handoff today:** extension builds `yt-dlp ...` command string -> Base64 -> `ytdlp://<cmd>||<cookies>||<user-agent>` (last two optional) -> hidden iframe -> Windows registry protocol handler launches `YTDLPHost.exe "<payload>"`. If the host is already running, the new process writes the payload to `%LOCALAPPDATA%\YT Downloader Pro\Payloads`, pings a named pipe, exits. Cookies therefore end up in a URL, a process command line and a file on disk.
- **Host** (`host/`): WPF app. Validates command with an allowlist (`CommandValidator`), queues tasks, runs `yt-dlp.exe` with ffmpeg and deno (downloaded to `%LOCALAPPDATA%\YTDownloaderProEngine`), shows queue UI, tray icon, toasts. Handles bulk jobs (playlists, "download all uploads") with a per-item summary, crop sections and live streams. Installer: Inno Setup (admin, HKLM+HKCU). CI: GitHub Actions on `windows-latest`.
- **YouTube specifics (from `main`):** the runner keeps yt-dlp warnings for YouTube, detects when YouTube offers only a legacy 360p-class format and reports "only Np offered by YouTube" in the result note, reads the cookie file to tell logged-in from logged-out sessions and words the bot-check error accordingly, and decodes yt-dlp output with the Windows ANSI code page. The extension sends all non-noise Google cookies (`cookieAllowAll`). The browser User-Agent is no longer forwarded for YouTube. Startup self-update uses `--update-to <channel>` (`UpdateChannel` in settings.json: nightly default, stable, master); `YoutubePlayerClients` is an emergency override.
- Typical command shape (validator-accepted): `yt-dlp -f "bv*[height<=1080]+ba/b" --merge-output-format mp4 -N 4 --no-playlist --restrict-filenames --embed-thumbnail --no-warnings --progress -o "~/Downloads/%(title)s_1080p.mp4" "https://..."`.
- **Native Messaging effective-choices rule (step 2.2):** the extension applies per-site gating before it sends options (subs only if the site supports it and not audio, and so on), so the host stays site-agnostic. The derivations are written down in `docs/NATIVE_PROTOCOL.md` and `tools/generate-native-golden.js`; the future `native.js` must copy them. Quirks of the current extension that the mapper reproduces on purpose (golden-tested): channel jobs always mux to mp4 even at 1440/2160 and have no audio-quality flag; `-S` (compat) is passed for audio too; the thumbnail flag is dropped for wav.

### Research basis (confidence noted)
- Chrome Native Messaging: host registered by a manifest file; location differs per OS; paths may be relative only on Windows, must be absolute on macOS/Linux; names are lowercase letters, digits, underscores and dots; `allowed_origins` takes no wildcards; the host gets the caller's origin as its first argument. **VERIFIED in step 2.1 against the Chrome docs page** (fetched). Edge/Brave/Firefox locations are still unverified.
- Message limits: JSON in UTF-8 with a 32-bit length in native byte order; host->browser at most 1 MB, browser->host up to 4 GB. **VERIFIED in step 2.1 (Chrome docs).** On Windows, Chrome checks the 32-bit registry view first, then 64-bit; the host must use binary stdout; `connectNative` keeps one process per port, `sendNativeMessage` starts one per message.
- Firefox: manifest uses `allowed_extensions` + gecko id; MV3 background uses `background.scripts` not `service_worker`. *(recalled; verify)*

### Gotchas learned (do not repeat)
- `UseWindowsForms` puts `System.Windows.Forms` in scope, so `Application` and `MessageBox` are ambiguous. In host code write `System.Windows.Application` / `System.Windows.MessageBox` fully qualified.
- `AppLogger` reads `AppPaths.Current.LogsDir` once, and keeps `host_debug.log` open. Anything that swaps `AppPaths.Current` (tests, Phase 3 startup) must keep logs out of folders it deletes, and must set paths before the first log call.
- Tests must never touch real settings/history/logs: `TestEnvironment` sandboxes them.
- Core types keep namespaces `YTDLPHost.Models` / `YTDLPHost.Services` / `YTDLPHost.ViewModels`, so host code needs no `using` changes. **XAML is the exception:** `MainWindow.xaml` maps `vm:` to `clr-namespace:YTDLPHost.ViewModels;assembly=YTDLPHost.Core` because `DownloadItemViewModel` now lives in Core. Any future type moved to Core and used in XAML needs the same `assembly=` mapping.
- Core must stay free of WPF: `main`'s copy buttons called `System.Windows.Clipboard`, so Core got `IClipboardService` (injected into `DownloadItemViewModel` and `MainViewModel`, implemented by `WpfClipboardService`). Same approach for any other WPF call that arrives from `main`.
- Services the view model needs from the platform go through `PlatformServices` (built by `WpfPlatform.Create()`), not through new constructor parameters or statics. Add an interface to `IPlatformServices.cs`, a field to the record, and the Windows implementation in `Wpf/`.
- Do not add `ConfigureAwait(false)` blindly: code after `await` in view-model flows relies on returning to the UI context (or uses `IUiDispatcher`). `DownloadQueue` uses it deliberately because every UI touch goes through the dispatcher.
- The owner's PC has .NET Desktop runtimes 9 and 10 but not 8 (the app targets 8): `dotnet run --project host/YTDLPHost` says "You must install or update .NET". Run it with `DOTNET_ROLL_FORWARD=Major` (Git Bash) or `$env:DOTNET_ROLL_FORWARD="Major"` (PowerShell), or install the .NET 8 Desktop Runtime. Also: the owner works in Git Bash, so PowerShell scripts are run as `powershell -ExecutionPolicy Bypass -File tools/x.ps1 ...`.
- Tests must NOT use the global `AppPaths.Current`: `AppPathsTests` swaps it and then deletes its temp folder while other test classes run in parallel, so a test that writes files through `AppPaths.Current` can fail that test at random (seen 2026-10-28 with the native sink cookie tests; fixed by giving them their own `IAppPaths` per test). Give each test its own temp root, as `EngineProvisionerTests` does.
- Test pipes made by `PipeRig` have no buffer on Windows: a write completes only when the other end reads. A test that writes several frames before it starts reading can hang (seen in `ShimBridgeTests`, 2026-10-30: 30 s timeouts). Write from a task and read in the test at the same time. This is a test-design matter; in real life the browser and the app always read.
- `DownloadIntake` holds a lock while it waits for the UI thread (`IUiDispatcher.Invoke`). Anything that is NOT on the UI thread must therefore never call `Submit`/`SubmitNative` directly: it could take the lock first and deadlock against a `ytdlp://` link handled on the UI thread. `NativeDownloadSink` runs the whole submit in one dispatcher call for this reason. Keep it that way.
- `PipeOptions.CurrentUserOnly` (verified in the .NET docs) checks the user account AND, on Windows, the elevation level. If the app is run "as administrator" and the browser (so the shim) is not, the shim cannot connect. Document it in step 2.6; do not weaken the option.
- A PowerShell/regex edit that swaps argument order or adds `\r\n` breaks the repo's LF convention; use Python with asserts on match counts.
- Git does not detect a file as moved when it changed a lot, so merging `main` into this branch resurrects old copies (modify/delete conflict) and can leave conflict markers. See the merge checklist in Section 0.
- `.gitignore` silently ignores `*.py`, `*.bat`, `*.exe` and `*.pem`. A new tooling file of one of these types is not committed unless `.gitignore` has a matching `!path` exception (`!tools/*.py` exists now). After adding any such file run `git status` and check it appears.

### Shim language decision (2026-10-28, researched)

**Update 2026-11-04: measured, the gate is met with the plain self-contained single-file build (median 109 ms), so that is what ships; Native AOT stays optional for later. The reasoning below still holds for choosing .NET over Rust/Go.**

**Decision: .NET Native AOT, linking the tested source files (`NativeFrame.cs` and the `NativePipe` class) instead of a second implementation.** Requirements it was judged against: tiny and fast to start, no runtime install, same-user-only access to the app, easy for the owner (a .NET developer) to maintain and debug, builds in the existing GitHub Actions matrix, low risk of antivirus trouble.

What the research found (sources: Microsoft Learn Native AOT docs and cross-compile page, Chrome native messaging docs, community reports):
- Chrome starts one host process per `connectNative` port and keeps it until the port closes; only `sendNativeMessage` starts a process per message. We use `connectNative`, so startup cost is paid once per popup or session, not per request. That weakens the usual argument for Rust/Go.
- Native AOT start-up is in the tens of milliseconds (one published benchmark: about 14 ms on Linux and 17 ms on Windows 11 for an ASP.NET app; a community hello-world measured about 2 ms and a 1.1 MB exe). Those are other people's machines and apps: hence the measure-it gate above. Rust or Go would be faster still, but not by an amount a person can notice here.
- Native AOT does NOT cross-compile between operating systems (no portable OS SDKs); only x64 to arm64 on the same OS. Cost for us: build the shim on each OS runner (the CI matrix already does) and have the C++ build tools installed on the owner's Windows PC (Visual Studio "Desktop development with C++" workload; clang and zlib on Linux). Self-contained single-file is the fallback if the owner will not install them.
- Security argument, the strongest one: the shim forwards cookies and URLs to whatever listens on the pipe name. `PipeOptions.CurrentUserOnly` on BOTH ends makes .NET check that the other side is the same user (and elevation level on Windows). A Rust or Go shim would have to re-implement that identity check by hand, and a mistake there lets another local process squat the pipe and receive cookies. Sharing `NativePipe` also keeps the pipe name and options identical on both sides by construction.
- Maintenance: one language, one toolchain, one CI setup, and the framing code the tests already cover. A Rust or Go shim would duplicate the framing and need its own tests and CI job.
- Antivirus: unsigned Go and Rust executables are widely reported to trigger Defender/SmartScreen heuristic detections (the `Wacatac.*!ml` family). I found no evidence that .NET AOT is safer; the community advice that actually helped was code signing. So this is NOT a reason to pick AOT; it is a reason to plan code signing of the shim and the app for releases, whatever language is used. A quarantined shim would silently break downloads.
- Rejected: using the WPF app exe itself as the native host (it is a GUI-subsystem process, and Chrome would start the whole app per port).

Shim rules that follow: link only `NativeFrame.cs` and the pipe-name/options class (do not reference all of Core: `NativeResponses` and the parser use reflection-based JSON, which Native AOT dislikes); the shim never parses the JSON, it only copies frames after the origin check; no `Console.Out` writes except frames (log to a file).

## 8. Using tokens well: what the evidence says

Goal: get the best result per token, **without** degrading quality by skimping. "Fewer tokens" is the wrong target; "fewer *irrelevant* tokens, and enough effort where errors are expensive" is the right one.

| Finding | Source (verified in an earlier session unless noted) | What it means for this project |
|---|---|---|
| Models use information best at the start and end of a long input and worse in the middle; accuracy also falls as input grows, even for long-context models | Liu et al., "Lost in the Middle: How Language Models Use Long Contexts" (arXiv 2307.03172; TACL 2024) | Keep Section 0 at the top of this file. Attach only the files a step needs. Do not paste whole repos "just in case". Restate the essential rule at the end of a long task |
| Context is a finite attention budget; the aim is the smallest set of *high-signal* tokens that makes the desired outcome likely. Related practices: load information just in time, keep notes outside the context window | Anthropic Engineering, "Effective context engineering for AI agents" (Sept 2025) | `PLAN.md` is the external note. Read the exact files a step touches (high signal) instead of skimming everything (noise) or skipping reads (missing signal) |
| Without external feedback, asking a model to review and correct its own reasoning often fails to help and can make results worse | Huang et al., "Large Language Models Cannot Self-Correct Reasoning Yet" (arXiv 2310.01798; ICLR 2024) | Trust compiler/test output and the owner's real error text over "let me re-check". That is why every step has a `dotnet test` count and a manual check, and why edits assert expected match counts |
| Letting a model write out intermediate reasoning improves multi-step problems | Wei et al., chain-of-thought prompting (2022). *Recalled, not re-checked* | Spend reasoning on the hard parts (the User-Agent injection was found by tracing the data flow, not by skimming; the queue races in 1.5c by reading the old scheduling code line by line) |

**Evidence caveat:** these studies measure long-context retrieval, self-correction and reasoning in general. None tests this exact workflow, so the rules above are sound inferences, not proven guarantees. The strongest practical safeguard remains running the tests.

### Concrete behaviors that follow
- **Read before edit, fully, in batches:** one command that reads every file the step needs. Re-read a file after it changes (a stale copy is a hidden assumption).
- **Skip re-reading** files already in context and unchanged in this chat, and skip files the step does not touch.
- **Ask or verify instead of guessing:** unknown API shape, line endings, a file's contents, a library's current behavior -> read it, search it, or request the output. State the confidence.
- **Spend more on:** security-relevant code, concurrency, anything that runs on users' machines, cross-platform path and process handling, and refactors that move many call sites. **Spend less on:** renames, docs, simple wiring.
- **Small steps:** one concern per step, one test count to confirm. Smaller diffs mean fewer errors and cheaper debugging.
- **Output discipline:** concise prose; never truncate code or tests in a deliverable; do not re-print what a zip already contains.
- **Fresh chat when context gets long:** quality can fall as a conversation grows. Start a new chat with the updated `PLAN.md` and the current code instead of continuing a very long thread.
